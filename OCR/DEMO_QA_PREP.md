# Demo Q&A 應答小抄

## 系統架構類

**Q: 為什麼要分成 LINE Bot 和網站兩塊，不整個做在 LINE 裡？**
A: LINE 對話框適合簡短互動（意圖判斷、查詢），但不適合複雜表單（四種文件
上傳、即時驗證是否齊全）。所以讓 LINE Bot 負責判斷「使用者想做什麼」，
複雜的申請流程交給網站處理，是職責分離的設計。

**Q: 這個系統能撐多少人同時使用？**
A: 目前是 Demo 等級架構（SQLite + 本機硬碟存檔），單機測試沒問題，但正式
上線需要換成 Postgres/MySQL + 雲端物件儲存（GCS/S3），並加上真正的身分
驗證機制，這些都列在專案 README 的「正式上線前要補強的地方」。

**Q: 資料放在哪裡？安全嗎？**
A: Demo 階段資料存在本機 SQLite 檔案與硬碟資料夾，未加密。正式上線前必須：
身分證字號/帳戶號碼等敏感個資要加密儲存、上傳的檔案要做存取權限控管
（不能任何人都能用網址直接看到）、全站要用 HTTPS。

## LINE Bot 技術類

**Q: LINE Bot 怎麼知道使用者傳了訊息？**
A: 用 Webhook 機制——LINE 官方伺服器收到使用者訊息後，會主動呼叫我們
設定好的網址（/webhook），不是我們主動去輪詢查詢。

**Q: 為什麼本機測試要用 ngrok？**
A: 本機電腦在家用/公司網路的 NAT 後面，沒有對外公開的網址，LINE 伺服器
沒辦法直接呼叫 localhost。ngrok 提供一個暫時的公開網址當中繼，把外部請求
轉發進本機。正式上線部署到雲端主機後就不需要 ngrok。

**Q: Channel Secret 是做什麼用的？**
A: 用來驗證「這個打進我們伺服器的請求，真的是 LINE 官方發的」，避免有人
假冒 LINE 傳假訊息攻擊我們的系統。這個驗證需要讀取請求的原始內容做加密
比對，所以程式碼裡 webhook 路由要掛在 JSON 解析中介軟體之前。

**Q: 怎麼知道申請進度是查到「本人」的資料，不會查到別人的？**
A: 每個 LINE 帳號都有官方發的唯一 userId。申請時把這個 userId 存進資料庫，
查詢時用同一個 userId 去比對，不同 LINE 帳號的 userId 對不上，查不到彼此
的申請紀錄。

## 表單 / 審核流程類

**Q: 為什麼四份文件要分開上傳，不是一次全部送出？**
A: 因為審核常常需要「補件」——如果是一次性送出、發現某一份文件有問題，
使用者要整案重來。分開上傳的話，只要重傳有問題的那一份即可，對申請人跟
承辦人員都比較方便。

**Q: 怎麼確認申請人真的設籍新竹市？**
A: Demo 階段是承辦人員在後台肉眼檢視身分證照片人工審核。正式上線可以考慮
加入 OCR 先做初步文字辨識比對，加速審核，但最終仍建議保留人工複核。

**Q: 怎麼確認是本人在申請，不是別人冒用？**
A: 目前用申請人填寫的完整身分證字號做核對。正式環境建議加強驗證機制，
例如搭配手機門號簡訊驗證、或要求存摺帳戶戶名與申請人姓名一致性檢查，
並且身分證字號屬敏感個資，資料庫應加密儲存、限制存取權限。

## Rich Menu 類

**Q: Rich Menu 按鈕點下去做了什麼？**
A: 本質上是「幫使用者自動打字送出訊息」——點左邊按鈕等同他自己手動輸入
「申請」，右邊等同輸入「查詢進度」，所以不需要另外寫處理邏輯，直接沿用
原本判斷文字內容的程式碼。

**Q: Rich Menu 圖片跟按鈕範圍要怎麼對應？**
A: 建立 Rich Menu 時要提供一組「座標範圍 + 對應動作」的清單（例如左半邊
0~1250px 對應「申請」），再上傳一張跟這個座標系統等比例的圖片蓋上去，
兩者要對齊圖片才會準確。

## AI 自動回覆類

**Q: LINE Bot 的 AI 自動回覆會不會亂回答、給錯誤資訊？**
A: 不會憑空回答。我們把官方公告的正確資訊（補助金額、資格、文件、聯絡方式等）整理成
一份「知識庫」文字檔，透過 System Prompt 要求 Gemini 只能根據這份資料回答，資料沒寫到
的細節會誠實說不確定並附上官方聯絡電話，不會憑自己的知識編造答案。這個做法在技術上
叫做「Grounding（資料落地）」，是簡化版的 RAG（檢索增強生成）。

**Q: 為什麼選 Gemini，不是其他家的模型？**
A: 這是可以替換的，程式架構上 AI 供應商是獨立模組，換成其他家 API 只需要改
`line.js` 裡呼叫 AI 的那段程式碼，不影響其他業務邏輯（申請導轉、進度查詢綁定）。

**Q: 官方公告內容更新了，Bot 的回答會不會跟著錯？**
A: 知識庫是獨立的文字檔（`knowledge-base.js`），跟程式邏輯分開，公告異動時只要改這
份文字檔重啟服務即可，不需要工程背景也能維護。

## 智慧審核 / OCR / 燈號機制類

**Q: AI 判錯怎麼辦？會不會有人被誤判紅燈但其實沒問題，或黃燈綠燈但其實有問題？**
A: 燈號只是「建議」，不是「決定」。系統設計上刻意讓 AI 只做初步分流，所有案件最終
狀態（核准/退件/補件）都要承辦人員在後台手動確認，AI 判定原因也會列出來給承辦人員
參考，不會有任何一個案件是全自動核准或全自動退件的。

**Q: OCR 準確度不夠怎麼辦？**
A: 目前用 Gemini 的圖片理解能力做 OCR，遇到辨識失敗或看不清楚的情況，系統會直接
標記「無法判讀」並歸類為黃燈（需人工確認），而不是假裝辨識成功或直接判定失敗。
這是刻意的保守設計：不確定的情況一律交給人工，不會讓 AI 在看不懂的時候亂猜。

**Q: 燈號判定的標準是怎麼定的？**
A: 目前是示範用的合理假設（金額誤差5%內算一致、20%以上算明顯異常），正式上線前
應該要跟實際承辦人員討論可接受的誤差範圍，這些數字都寫在 `rules.js` 裡容易調整。

**Q: 為什麼設籍地址檢查只查身分證背面，正面不用查？**
A: 台灣國民身分證的住址欄位印在背面，正面只有姓名、出生日期、身分證字號等資訊，
所以地址比對是讀身分證背面的 OCR 結果，這是刻意對應真實證件版面設計的。

**Q: LINE 通知會不會太頻繁打擾使用者？**
A: 目前只在「申請送出成功」跟「承辦人員變更狀態」這兩個時間點推播，不會有其他
主動通知，且都是使用者關心的關鍵進度節點。
