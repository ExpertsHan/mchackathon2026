# 新竹市 AI 補助申請 - 智慧審核系統 Demo

民眾直接在我們自己做的網站申請、上傳文件，AI 自動 OCR 比對文件內容，用規則引擎
分成綠燈/黃燈/紅燈提供承辦人員參考，狀態變更透過 LINE 主動通知申請人。

## 這個 Demo 想解決什麼問題

題目提到市府面臨「審核、核銷、撥款進度追蹤」繁重的行政作業。目前承辦人員審核
每一件申請，都要人工看身分證地址是否為新竹市、對發票金額、比對品名跟申請填寫的
是否一致——這些都是重複性高、可以先讓 AI 做初步篩選的工作。

這個系統示範的重點不是「取代承辦人員」，而是**把明顯沒問題的案件快速篩出來，把
承辦人員的注意力留給真正有疑點的案件**，並且讓民眾不用主動詢問就能收到進度通知。

## 架構總覽

```
民眾在 LINE 傳「申請」
   → Bot 回我們自己的申請網頁連結（?uid=帶入LINE使用者ID，之後不用再額外綁定）
   → 民眾填寫姓名/電話/申請工具名稱/付款金額，上傳身分證正反面、發票、存摺、（弱勢證明）
   → 每上傳一張「發票」「身分證背面」，後端立刻用 Gemini 做 OCR，擷取金額、工具名稱、地址
   → 民眾按下「送出申請」
        → 規則引擎比對：申請填寫資料 vs OCR 擷取資料
        → 判定燈號：🟢綠燈（快速確認）/ 🟡黃燈（需承辦人確認）/ 🔴紅燈（需深入審查）
        → LINE 推播：申請已送出通知

承辦人員登入後台
   → 案件列表直接看到燈號，點開可看到 AI 判定原因、OCR 擷取結果 vs 申請人填寫的對照表、文件縮圖
   → 人工決定最終狀態（審核中/需補件/已核准/已撥款/不通過），燈號只是參考，不會自動核准
   → 按下儲存，系統自動用 LINE 推播通知申請人最新狀態

民眾在 LINE 傳「查詢進度」
   → 直接查詢名下所有申請案的狀態（因為申請時就已經記錄 LINE 帳號，不需要額外綁定）
```

## 智慧審核的判定邏輯（`rules.js`）

| 檢查項目 | 綠燈條件 | 黃燈條件 | 紅燈條件 |
|---|---|---|---|
| 設籍地址 | OCR讀到地址包含「新竹市」| OCR辨識失敗/欄位無法判讀 | OCR讀到地址明確不是新竹市 |
| 付款金額 | 與申請填寫金額誤差在5%內 | 誤差5%~20%，或OCR辨識失敗 | 誤差超過20% |
| 工具名稱 | 申請填寫與OCR品名可以互相對應 | 對不太起來，或OCR辨識失敗 | （目前設計為最多黃燈，不單獨判紅燈，因為工具名稱寫法本來就會有落差）|

**重要原則：規則引擎只給建議，不做最終決定。** 任何一項紅燈就整案判紅燈，都沒有紅燈但有黃燈就判黃燈，
全部通過才是綠燈；但不管燈號是什麼，最終核准與否，一律由承辦人員在後台手動點選決定。

## 安裝與啟動

```bash
npm install
cp .env.example .env   # 填入 ADMIN_TOKEN、LINE 相關設定、GEMINI_API_KEY、PUBLIC_BASE_URL
npm start
```

- 民眾申請頁：`http://localhost:3000/apply.html?uid=demo-user-001`
- 承辦人員後台：`http://localhost:3000/admin.html`（用 `.env` 裡的 `ADMIN_TOKEN` 登入）

## API 一覽

| Method | Path | 用途 | 需要驗證 |
|---|---|---|---|
| POST | `/api/applications` | 建立申請案，回傳 `id` 與 `access_token` | 無 |
| POST | `/api/applications/:id/documents/:docType` | 上傳單一文件（`receipt`/`id_back` 會自動觸發背景 OCR）| `x-access-token` |
| POST | `/api/applications/:id/submit` | 送出申請：檢查文件齊全 → 等待OCR完成 → 執行規則引擎 → 判定燈號 → LINE通知 | `x-access-token` |
| GET | `/api/applications/:id` | 查詢單一申請案 | `x-access-token` |
| GET | `/api/applications/:id/documents/:docType/file` | 讀取文件檔案 | `x-access-token` 或 `x-admin-token` |
| GET | `/api/status?uid=` | LINE Bot 用：依 LINE 使用者查所有申請案狀態 | 無（見下方安全性說明）|
| GET | `/api/admin/applications` | 後台：案件列表（含燈號）| `x-admin-token` |
| GET | `/api/admin/applications/:id` | 後台：單一案件詳細（含OCR結果、判定原因、文件）| `x-admin-token` |
| PATCH | `/api/admin/applications/:id` | 後台：更新狀態/備註，狀態變更會自動觸發 LINE 推播通知 | `x-admin-token` |

## 加上 AI 自動回覆（Gemini + 知識庫）與 OCR 比對

兩個功能都用同一個 `GEMINI_API_KEY`：
- **AI 客服**（`line.js` 的 `askAI`）：回答自然語言問題，依照 `knowledge-base.js` 的官方資料回答
- **OCR 文件比對**（`ocr.js`）：讀取發票/身分證背面圖片，用 Gemini 的圖片理解能力擷取結構化資料

### 設定方式

1. 到 [Google AI Studio](https://aistudio.google.com/apikey) 申請免費的 Gemini API Key
2. 填進 `.env` 的 `GEMINI_API_KEY`
3. `npm install`，`npm start` 重開

沒有設定 `GEMINI_API_KEY` 的話：AI 客服會退回固定文字回覆；OCR 會回傳 `skipped`
狀態，規則引擎會把這種情況當成「無法判讀」，判定為黃燈（需人工確認），**不會讓
系統壞掉，只是少了自動化判斷的部分**。

## 授權設計（沿用先前修過的授權缺失防護）

- 每個申請案有獨立的 `access_token`，操作/查看都要帶這把金鑰，光知道申請編號不夠用（避免 IDOR）
- `/uploads` 資料夾不公開，檔案要透過需驗證的路由讀取
- 補件時舊檔案會被刪除，只留最新一份
- Token 比對用固定時間比對（`crypto.timingSafeEqual`），避免時序攻擊
- `/api/status?uid=` 目前仍未加驗證，因為呼叫方是伺服器對伺服器的 LINE webhook；嚴謹作法應該
  再加一層伺服器對伺服器的驗證，不要讓瀏覽器能直接呼叫

## Demo 時怎麼跑一次完整流程

1. LINE 傳「申請」→ 點連結開啟申請頁（本機測試可以直接開 `apply.html?uid=demo-001`）
2. 填寫資料，工具名稱填「ChatGPT Plus」、金額填 990（示範綠燈用）
3. 上傳四份文件（隨便找圖片測試即可）
4. 送出申請，觀察 LINE 是否收到「已送出」的推播通知
5. 打開 `admin.html`，應該能看到這筆案件的燈號、AI 判定原因、OCR 對照表
6. 把狀態改成「已核准」，觀察 LINE 是否收到核准通知

如果想示範黃燈/紅燈，可以刻意把申請表單填寫的金額跟實際發票金額填不一樣（例如
申請填 3000 但發票內容是 300），或上傳非新竹市地址的身分證背面。

## 正式上線前要補強的地方（Demo 先跳過）

- **OCR 準確度**：Gemini 的圖片理解不是專門訓練的 OCR 模型，遇到模糊、傾斜的照片
  準確度會下降，正式環境建議搭配影像前處理（旋轉校正、對比度調整）或專門的 OCR API
- **規則引擎的閾值**：目前金額誤差 5%/20% 這些數字是示範用的合理猜測，正式上線需要
  跟承辦人員討論實際容許誤差
- **身分驗證**：後台目前只用一組固定 Token，正式環境要換成正式登入 + 權限控管
- **檔案儲存**：目前存在本機磁碟，正式環境建議存到雲端物件儲存（如 GCS/S3）
- **個資保護**：身分證字號、存摺帳號屬敏感個資，資料庫欄位應加密
- **HTTPS 與速率限制**：正式站台需要 HTTPS，並對上傳/OCR 相關 API 加上速率限制
